# Directory sweep — 2026-08-15

Every directory in both repositories, read for bugs. This is the raw list: what
was found, whether it was verified or only read, and whether it is fixed.

Ordered by severity within each section. Things that *look* like bugs and are
not are at the bottom — those cost as much to re-investigate as real ones.

Nine findings. Four are fixed in this branch, five are open.

---

## Fixed in this sweep

### F1. Four username refusals had no message — SITE · `src/invite/api.ts`

**Verified. Fixed.**

`validateUsername` emits eight reasons. The site's map had four, and the other
four — `mixed-scripts`, `bad-start`, `bad-end`, `double-separator` — fell
through to the generic fallback:

> "Something went sideways on the gate's end. Try again in a minute."

Which is worse than silence. The name was refused *correctly*; the writer is
told the server is broken and to wait. They retype the same name, wait, retype
it. Nothing on screen ever hints why, and nothing they can do will work.

A fifth was simply wrong: `username-bad-characters` read "lowercase letters,
digits and underscores only" — text that predates hyphens and both new
alphabets, describing a rule the gate stopped enforcing.

The app's own mirror in `src/utils/penName.js` has had all eight since the
rules changed, so this was the site half alone. `npm run check:headers` now
compares the two lists and fails when a reason has no sentence.

### F2. The Linux launcher entry froze on the day you first picked an icon — APP

**Verified against a fake XDG tree. Fixed.**

`linuxIconTheme` writes a per-user `.desktop` by copying the installed one and
repointing `Icon=`. A user-level file of that name shadows the system entry
*entirely* — `Exec`, `MimeType` and all — and it was written once, on the icon
change, and never touched again.

So it froze whatever the installed entry said that day. `com.aurorastudios.authno`
was added to the protocols block for the extension OAuth work; anyone who had
picked a non-default icon before that update kept a `.desktop` registering
`x-scheme-handler/authno` alone, and an extension's redirect had no handler to
come home to. Permanently, silently, and only for users who touched the picker.

Now rebuilt from the current system entry at startup.

### F3. Extension UI pages could not do their own OAuth — APP

**Fixed.** Known issue 6. The background half had `host.oauth`; a `ui-file`
page's bridge proxied `openBrowser` and stopped. The round trip is now
`oauthRoundTrip`, shared rather than copied, so the redirect-scheme guard
travels with it.

### F4. `.gitignore` did not cover the desktop build output — APP

**Verified the hard way. Fixed.**

`directories.output` is `dist-electron`; only `dist/` was listed. A desktop
build leaves 775 MB of unpacked Electron in the working tree, and `git add -A`
sweeps it in — including a 251 MB `app.asar` that GitHub refuses. The push
fails with `remote end hung up`, which names neither the file nor the reason.

## Open

### O1. `MainActivity` leaks a file descriptor on a failed read — APP · `android/`

**Read, not run** — Gradle cannot resolve its plugins offline here.

Three sites in `MainActivity.java` (lines 98, 250, 300, 343) and one in
`ExtbkAssetsPlugin.java` (98) do:

```java
InputStream is = getContentResolver().openInputStream(uri);
...
while ((n = is.read(chunk)) != -1) buf.write(chunk, 0, n);
is.close();
```

`close()` is after the loop, not in a `finally`. A read that throws part-way —
a content URI whose provider died, a file removed mid-import, a truncated
stream — leaks the descriptor. Opening books repeatedly in one session
accumulates them until `EMFILE`.

`FilePickerPlugin.readAllBytes` already does this correctly with
try-with-resources; these four did not get the same treatment.

**Fix:** try-with-resources, exactly as `FilePickerPlugin` does it.

### O2. A long-press that unmounts leaks a document listener — APP · `Sidebar.jsx`

**Read.** `onTouchStart` adds a `touchmove` listener on `document` and stores
its remover in `longPressCleanup.current`. Only `onTouchEnd` calls it.

Two ways it survives:

- The component unmounts mid-press — the long-press opens a context menu that
  navigates — so `onTouchEnd` never fires.
- A second `onTouchStart` before the first ends (a second finger) overwrites
  `longPressCleanup.current`, orphaning the first listener permanently.

Each orphan holds a closure over that render's state. Small, and it accumulates
only under repeated long-presses, but it is unbounded.

**Fix:** call the cleanup at the top of `onTouchStart`, and again from an
unmount effect.

### O3. The picker previews one icon and desktop applies another — APP

**Verified by looking at the images.**

| | artwork |
|---|---|
| Picker preview, "Dark" (`app-icons/ic_launcher_default.png`) | round, lone `a` |
| Android `IconDefault` (`mipmap/ic_launcher`) | round, lone `a` |
| Windows startup (`authno.ico`) | squircle, lone `a` |
| `ICON_ASSETS.default` + `linux.icon` (`authno-512.png`) | **the "authno" wordmark** |

Every other icon id maps to the same file as its preview. `default` is the only
one that does not, so on desktop the tile you press and the icon you get are
different pictures.

**Not fixed because the resolution is a brand decision**, not a defect with one
obvious answer: either desktop adopts the `a` mark everywhere, or the preview
becomes platform-aware. Three of the four surfaces already say `a` mark.

### O4. Nothing checks the app can read what the CLI writes — APP · `extensions/`

**Verified compatible today**, but unguarded.

The `.extbk` format has two independent implementations: the CLI writes it
(node `zlib`, its own Reed-Solomon copy) and the app reads it (`pako`, its own).
`extensions/extbk-cli`'s `npm test` is `node src/cli.js --help`, and the CI
round-trip is CLI-writes → CLI-reads.

A shared misreading of the format is therefore invisible: both halves would
agree with each other and disagree with nothing. Extension authors would ship
files no app could open, and the CLI's own suite would stay green.

I built a real `.extbk` with the CLI — nested assets, a relative import, a
UTF-8 asset — and decoded it with the app's `validateExtbk`/`unpackExtbk`.
Everything round-tripped, bytes intact. **The implementations agree today.**
Nothing keeps them agreeing.

The two `reedSolomon.js` copies already differ by one function (`gfInv`, dead
code in the CLI). That is harmless and is exactly the shape of the drift that
would not be.

**Fix:** one CI step — build a fixture with the CLI, decode it with the app's
reader, compare. About fifteen lines.

### O5. The appstream comment names a file that does not ship — APP · `appstream/`

**Read.** The header says the component id "MUST match the .desktop file
basename (com.aurorastudios.authno.desktop)". The `.desktop` that actually
installs is `authno.desktop` (`package.json` → `desktopName`).

The file itself is *correct* — `<launchable type="desktop-id">authno.desktop</launchable>`
is what AppStream requires when the id does not end in `.desktop`, and that is
what is there. Only the comment is wrong, and it is wrong in the direction that
would make someone "fix" a working file.

## Looks like a bug, is not

Each of these cost real time to rule out. They are here so the next sweep does
not spend it again.

- **`BootReceiver` is `android:exported="false"` with a `BOOT_COMPLETED`
  filter.** Correct. `exported` governs *non-system* senders only — the
  documented wording is "can receive messages from non-system sources outside
  its application" — and `BOOT_COMPLETED` comes from the system. `false` is
  Google's own recommendation for a receiver that only takes system broadcasts.

- **`disarm()` cancels every slot with the name `"evening"` hardcoded.** Fine.
  A `PendingIntent` is keyed on `(requestCode, Intent)` and `filterEquals`
  ignores extras; the slot name is an extra, while the index is in both the
  request code and the intent's `data` URI. Cancellation matches on the parts
  that identify it.

- **Every `PendingIntent` in `android/`.** All nine declare `FLAG_IMMUTABLE`.
  The API-31 crash is not there.

- **`ExtbkAssetsPlugin` builds an assets path from a caller-supplied
  filename.** Guarded by `^[\w.\-]+\.extbk$` before use — no slashes, so no
  traversal.

- **Two `zlib` implementations across the format.** `pako` in the app, node's
  `zlib` in the CLI. Both emit and read standard zlib streams; O4 confirmed a
  real file crosses cleanly.

- **`src/utils/rs.js` duplicated into the CLI.** Byte-identical.

- **Timer and listener balance across `src/`.** Swept every file: one real
  imbalance (O2). `sounds.js` attaches to an `Audio` element that is collected
  with it; `sandboxProtocol.js`'s listener lives inside the frame document and
  dies with the iframe.

- **`versionName` is unset in `android/app/build.gradle`.** Injected by CI as a
  Gradle property; a local build is deliberately `1.0-local`.
